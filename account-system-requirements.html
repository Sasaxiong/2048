1.2 系统边界与职责

最重要的边界：账户系统 vs 支付网关 支付网关负责"能不能付"（验证、授权、路由、委托令牌验证、风控拦截）；账户系统负责"付了怎么记"（入账、记账、维护余额、生成流水）。AI 代理委托令牌验证由支付网关完成，账户系统仅在流水中记录已验证的代理 ID 供审计追溯，不参与验证决策。

2.3 多维余额索引模型（核心设计）

物理隔离 vs 多维余额索引 传统物理隔离（每种状态一张表）灵活性差，新增状态需建表；纯状态标记无法快速查余额。本系统采用"主账簿流水（不可变事件溯源）+ 多维余额索引（实时更新）"方案：流水永不修改，状态变更也生成新流水；余额索引按三维实时维护，O(1) 毫秒级查询；快照+增量模式保证期初期末连续。
-- ① 余额索引表：三维主键，O(1) 查询 CREATE TABLE balance_index ( account_id VARCHAR(64) NOT NULL, -- 子账户 ID currency VARCHAR(3) NOT NULL, -- 币种: JPY | USD | HKD … dimension VARCHAR(24) NOT NULL, -- AVAILABLE|PENDING|FROZEN_RISK|FROZEN_LEGAL|FROZEN_DISPUTE|SUSPENSE|AUTH_HOLD balance BIGINT NOT NULL DEFAULT 0, -- 最小货币单位（JPY 无小数，USD 分） version BIGINT NOT NULL DEFAULT 0, -- 乐观锁版本号 last_updated TIMESTAMP NOT NULL, PRIMARY KEY (account_id, currency, dimension), INDEX idx_account_currency (account_id, currency) ); -- ② 查询商户可用余额：O(1) 主键点查 SELECT balance FROM balance_index WHERE account_id = 'ACC_MCH_001_WITHDRAWABLE' AND currency = 'JPY' AND dimension = 'AVAILABLE'; -- 毫秒级 -- ③ 余额更新：CAS 乐观锁，防并发超提 UPDATE balance_index SET balance = balance + :delta, version = version + 1, last_updated = NOW() WHERE account_id = :account_id AND currency = :currency AND dimension = :dimension AND version = :expected_version -- 版本号 CAS AND (:delta > 0 OR balance >= ABS(:delta)); -- 负向操作检查余额 -- affected rows = 0 → 乐观锁冲突或余额不足，应用层重试或告警

余额维度说明

维度代码含义计入可用触发事件解除条件
AVAILABLE可用余额（可提现）✓ 是结算完成（SETTLED）-
PENDING在途待结算✗ 否交易捕获（AUTH_CAPTURED）价值日期到达 → 转 AVAILABLE
AUTH_HOLD预授权占用✗ 否预授权请求（AUTHORISED）捕获 → 转 PENDING；撤销 → 释放
FROZEN_RISK风控冻结✗ 否风控规则触发风控审核通过，人工解冻
FROZEN_LEGAL法律冻结✗ 否法院命令法院撤销冻结令
FROZEN_DISPUTE争议冻结✗ 否拒付/争议发起争议胜诉解冻；败诉划出
SUSPENSE暂记待查✗ 否对账差错发现差错查清，完成调账
为什么冻结要分三个维度？ (1) 解冻条件完全不同：风控冻结需人工审核，法律冻结需法院撤销，争议冻结需争议结案；(2) 审计追溯必须区分冻结原因；(3) 统计报表需分类分析冻结原因。三个维度共享同一个 balance_index 表结构，不增加系统复杂度。

3.2 状态转换规则

核心原则：状态变更即流水 任何状态变更（包括冻结/解冻/结算）均生成一条新的流水记录，原始流水永不修改。这保证了：(1) 任意时刻的余额快照可以通过历史流水完整重建；(2) 期初期末余额始终连续；(3) 审计线索完整。

4 账务前置引擎

4.1 架构与职责边界

账务前置引擎接收业务系统通过消息队列发布的业务事件，根据配置的入账规则，自动执行多步骤的伞形下沉入账流程。

4.6 集团分润配置

当集团（L3代理）需要从商户交易中抽取管理费时，通过独立配置表 + 自定义函数动态获取费率，一条规则适配所有集团，无需为每个集团创建独立规则。

开发注意：getGroupFeeRate() 函数实现要求 表达式 getGroupFeeRate($.merchant_id) * $.pay_amount 需要开发在表达式引擎（推荐 Aviator/QLExpress）中注册自定义函数 getGroupFeeRate。函数逻辑：按 merchant_id 查询 group_fee_config 表，返回 fee_value（BigDecimal）。必须支持 Redis 缓存（TTL 300s），配置变更时主动清除缓存；查询不到时返回默认值 0。若表达式引擎不支持函数注册，可改用配置化 DB_QUERY 类型金额规则，或要求上游在事件中直接传递 $.group_fee_rate 字段（最简单方案）。

6.2 差错类型与处理机制

核心原则：不修改原始记录，只增加新流水 任何差错处理、调账操作均通过生成新的账簿流水和会计分录实现。原始流水标记为不可变（只读），保证完整的审计线索。
差错类型识别方式发现时处理查清后处理流水变化
平台单边账
系统有记录，通道无		系统交易ID在通道报表中缺失生成暂记流水：SUSPENSE +amount；余额索引 PENDING -amount, SUSPENSE +amount通道确认后补单；或核销冲正增加：暂记流水（差错单号标注）
通道单边账
通道有记录，系统无		通道报表中有交易ID，系统无对应记录生成入账流水：SUSPENSE +amount；人工确认来源确认是真实交易则补单入账；否则退回通道增加：暂记流水 + 后续补单流水
金额不一致
两边都有，金额差异		系统金额 ≠ 通道报表金额差额进暂记：SUSPENSE +abs(diff)与通道协商：收到补差 or 退回多收增加：差额暂记流水 + 调整流水
重复入账
同一交易多次入账		幂等键检测（Redis+DB）拦截于入账前，不产生流水；触发告警若已入账：人工审核核销冲正拦截成功则无流水；已入账则增加冲正流水
退款失败

7 清结算设计

7.1 结算周期与价值日期

两步解耦设计 步骤一（PENDING → AVAILABLE）：由"价值日期到达"事件触发，系统自动执行，与出款频率无关；步骤二（AVAILABLE → PAID_OUT）：由"出款指令"触发，按商户配置的出款频率或手动申请执行。两步解耦使结算状态准确，出款时机灵活。
步骤触发时机余额变化会计分录执行方式
① PENDING → AVAILABLE价值日期（Value Date）≤ 今日；默认 T+1PENDING -amount, AVAILABLE +amount借：2201 / 贷：2202日终批量自动，无需人工
② AVAILABLE → PAID_OUT结算周期到达（每日/周/月）或手动申请AVAILABLE -amount借：2202 / 贷：1122（银行）三层审核后执行

7.2 清分服务（结算时分润）

清分服务与账务前置引擎解耦 账务前置引擎（交易时实时执行）负责通道入账、手续费记录、商户待结算入账；清分服务（结算周期批量执行）负责从待结算资金中扣除集团分润，生成最终可提现余额。两者分开的原因：分润计算依赖历史汇总数据，不适合实时计算；清分失败不影响交易入账；结算策略可灵活配置。

7.3 出款流程（三层审核模型）

三层审核模型（应对财务对自动化出款的顾虑） 第一层：出款批次预览（财务点击确认，获得心理掌控感）；第二层：异常驱动审核（风控标记可疑交易，进人工审核池）；第三层：事后对账（每日自动生成对账报告，财务核对）。核心哲学：让机器处理所有符合预期的交易，让人处理不符合预期的例外。

9.3 批量报表并发处理

月结报告 / 结算单的并发生成策略 1. 异步任务队列：生成任务放入 MQ（RocketMQ/Kafka），Worker 池异步消费，避免同步阻塞； 2. 数据快照：报表查询 = 日终余额快照 + 当日增量流水，历史月份直接读快照（无需全表扫描）； 3. 任务幂等：每个结算周期维护生成状态字段，防止重复触发； 4. 读库分离：报表查询走只读副本，不影响主库写入； 5. 分页流式输出：超大结果集采用游标分页，避免 OOM。
