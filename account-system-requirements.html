1.1 背景与目标

本系统为外卡收单业务的核心账务基础设施，负责管理从收单通道入账到商户结算的完整资金流转。系统参考 Stripe、Adyen、Revolut、Fiserv、Worldpay 等国际主流支付机构的账户设计范式，结合公司业务实际（日本市场 KPay 外卡收单），设计一套高可用、可扩展、可审计的账户体系。

2.3 多维余额索引模型

核心设计理念：不采用多个物理子账户表，而使用"主账簿流水 + 多维余额索引"的方式。流水不可变，状态变更也作为新流水记录。余额索引按（账户ID + 币种 + 资金状态维度）实时更新，支持 O(1) 毫秒级余额查询。

余额索引表结构

-- 多维余额索引表 CREATE TABLE balance_index ( account_id VARCHAR(64) NOT NULL, -- 子账户ID currency VARCHAR(3) NOT NULL, -- 币种: JPY, USD, HKD... dimension VARCHAR(20) NOT NULL, -- AVAILABLE|PENDING|FROZEN|SUSPENSE|AUTH balance BIGINT NOT NULL DEFAULT 0, -- 金额（最小货币单位） version BIGINT NOT NULL DEFAULT 0, -- 乐观锁版本号 last_updated TIMESTAMP NOT NULL, PRIMARY KEY (account_id, currency, dimension), INDEX idx_account_currency (account_id, currency) );

余额维度说明

维度（dimension）含义计入可用余额触发事件
AVAILABLE可用余额（可提现）是结算完成事件
PENDING待结算（在途）否交易授权/捕获事件
FROZEN_RISK风控冻结否风控规则触发
FROZEN_LEGAL法律冻结否法院命令
FROZEN_DISPUTE争议冻结否拒付/争议发起
SUSPENSE暂记（差错待查）否对账差异发现
AUTH_HOLD预授权占用否预授权请求
关键设计决策：风控冻结、法律冻结、争议冻结使用独立的维度标记，不混用同一个 FROZEN 维度。原因：(1) 解冻条件不同（风控需要人工审核，法律冻结需法院撤销）；(2) 审计追溯需要区分冻结原因；(3) 统计报表需要分类汇总。每次冻结/解冻操作同时生成一条状态变更流水，保证全生命周期可追溯。

三、资金状态机

3.1 资金状态定义

每笔资金从进入系统到最终出款，经历以下状态。状态变更均生成新的流水记录，确保全程可追溯。

3.2 关键说明：预授权不单独入账

设计决策：预授权（AUTHORISED）阶段不做账簿入账，仅在余额索引中标记 AUTH_HOLD 以防止超提。入账从"预授权完成（AUTH_CAPTURED）"事件开始。原因：预授权可能被撤销，撤销前入账会产生不必要的流水；收单通道对预授权不计费，无需生成会计分录。

3.3 冻结与解冻流程

关键设计：冻结操作会从 AVAILABLE 维度扣减余额，加入对应的冻结维度（FROZEN_RISK / FROZEN_DISPUTE / FROZEN_LEGAL），同时生成一条状态变更流水（金额为0，类型为 FREEZE）。解冻时反向操作。这样确保：(1) 快速查询各维度余额；(2) 任意时刻的余额快照可重建；(3) 差错留观中的账户即使未解决，也能准确显示各维度余额。

四、账务前置引擎

4.1 规则引擎设计

账务前置引擎接收业务系统发出的业务事件，根据配置的入账规则，自动执行多步骤入账操作。规则引擎与账户系统之间通过明确的职责边界解耦。

职责边界说明：账务前置引擎负责"付了怎么记"（入账、记账）；支付网关负责"能不能付"（验证、授权、路由）。委托令牌验证、智能路由等均由支付网关完成，账务系统仅接收已验证通过的入账指令，并在流水中记录代理ID等元数据。

4.2 入账步骤：伞形下沉模型

伞形下沉是本系统核心入账模式：资金从通道应收款逐步流入各层级账户，保证资金流向清晰可控。

无负余额原则：所有子账户不允许负余额。因此入账步骤顺序至关重要：必须先增加后减少。对于退货等需要先从下层账户划出的场景，应先将资金归集至中间账户（增加），再分配到目标账户（减少），确保每一步操作后余额均为非负值。

4.4 集团分润配置

当集团需要从商户交易中抽取管理费时，通过独立的分润配置表 + 自定义函数动态获取费率，无需为每个集团创建独立规则。

6.2 差错处理原则

核心原则：不修改原始记录，只增加新流水。任何差错处理、调账操作均通过生成新的流水记录实现，原始流水永不修改。这确保了审计线索的完整性。
差错类型发现时处理查清后处理
平台单边账生成冲正暂记流水；余额索引：SUSPENSE +amount查清原因，生成调整流水还原或确认核销
通道单边账生成暂记入账流水；余额索引：SUSPENSE +amount通道确认后，转出暂记，生成正式入账

6.3 暂记账户设计

暂记账户（SUSPENSE）是系统的"安全网"：所有无法立即确认归属的资金，都先进暂记账户，确保系统借贷平衡，同时不影响其他账户的正常运作。暂记账户的余额应每天监控，超过 T+3 未处理的需自动告警。

七、清结算设计

7.1 结算周期与资金转移

两步转移设计：(1) PENDING → AVAILABLE 由"结算事件"触发（价值日期到达），与出款频率无关；(2) AVAILABLE → PAID_OUT 由"出款指令"触发，按商户配置的出款频率执行。两步解耦确保结算状态准确，出款时机灵活。
步骤触发条件账户变化会计分录

AVAILABLE → PAID_OUT结算周期到达（每日/每周/每月）或商户手动申请可提现余额减少借：2202（可提现）/ 贷：1122（银行）

九、并发控制与幂等性

9.1 幂等性控制

幂等性是账务系统的核心安全机制，防止因网络重试、系统重启等导致的重复入账。

三层拦截架构

第一层：Redis 分布式锁
事前拦截：请求进来先抢锁，抢不到直接返回"处理中"
第二层：数据库唯一约束
事中拦截：幂等键 DB 唯一索引，写入重复抛异常
第三层：状态机版本号
逻辑拦截：乐观锁 version 字段，并发更新余额防止超提

幂等键设计

-- 幂等键格式 "idem:{transaction_id}:{rule_id}:{step_no}:{account_id}" -- 示例 "idem:TXN-20260418-00123:RULE_SCE_PURCHASE:3:ACC_KPAY_TRD_001" -- 幂等记录表 CREATE TABLE idempotency_record ( idem_key VARCHAR(200) PRIMARY KEY, status VARCHAR(20), -- PROCESSING | SUCCESS | FAILED result TEXT, -- 执行结果快照 created_at TIMESTAMP, expired_at TIMESTAMP -- TTL: 24小时 );

重复请求处理策略

检测结果处理方式返回给调用方
NOT_EXIST正常执行入账200 + 入账结果
PROCESSING等待或返回处理中202 Processing
SUCCESS返回缓存的成功结果（不重复入账）200 + 历史结果
FAILED需人工确认后决定是否重试409 + 错误详情

9.2 并发控制

-- 余额更新：乐观锁防并发超提 UPDATE balance_index SET balance = balance + :delta, version = version + 1, last_updated = NOW() WHERE account_id = :account_id AND currency = :currency AND dimension = :dimension AND version = :expected_version -- 版本号匹配，CAS AND balance >= :abs_delta; -- 余额充足（仅负向操作需此条件） -- 影响行数 = 0 时，表示并发冲突或余额不足，需重试或告警

批量结算单并发处理

批量报表并发策略： (1) 异步队列：结算单/月结邮件生成任务放入队列（如 RocketMQ），Worker 池异步消费，避免同步阻塞； (2) 数据快照：查询使用"日终余额快照 + 当日增量流水"组合，历史月份直接读快照； (3) 任务幂等：每个结算周期维护生成状态，防止重复触发； (4) 读库分离：报表查询走只读副本，不影响主库写入。

原则具体实现参考来源
状态变更即流水所有余额维度变化（冻结/解冻/结算）均生成新流水，原始流水永不修改Worldpay 事件溯源模式
多维余额索引按（账户ID + 币种 + 状态维度）建立余额索引，O(1)查询Stripe/Adyen 架构
快照+增量日终生成余额快照，报表查询 = 快照 + 增量，兼顾效率与准确Worldpay 报表模式
价值日期标记用日期/状态标记资金性质替代物理隔离，提升灵活性Adyen Value Date
无负余额原则伞形下沉步骤遵循"先增后减"顺序，任意步骤后余额均非负本系统设计
幂等+原子性三层幂等拦截 + 单事务多步骤入账，要么全成功要么全失败行业最佳实践
职责边界清晰账户系统只负责入账记账，验证/路由/授权由支付网关负责架构设计原则
