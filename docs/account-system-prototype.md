# 账户系统原型设计

## 1. 文档目标

本文以产品原型说明的方式定义账户系统的核心能力，覆盖：

- 业务账户：面向用户、商户、平台等业务主体的账户开立、查询、冻结、余额管理与业务交易承接。
- 账务前置：面向业务事件的入账规则配置、事件匹配、入账指令生成与指令状态跟踪。
- 会计核心：面向资金事实的复式记账、会计分录、账务试算、日终对账与审计追踪。

目标是让产品、研发、测试、运营、财务可以基于同一套账户语义完成需求评审、接口设计、原型绘制和测试验收。

## 2. 背景与范围

### 2.1 建设背景

业务增长后，钱包余额、商户结算款、平台手续费、保证金、退款、冻结金额等资金形态会快速增加。如果只用业务订单表维护余额，容易出现：

- 交易成功但余额未更新，或余额更新但订单状态未闭环。
- 可用余额、冻结余额、在途金额口径不一致。
- 财务无法还原每一笔资金变动的借贷关系。
- 对账只能靠人工导出明细核对，问题定位成本高。

因此需要将“业务账户”和“会计核心”分层：业务账户服务业务体验和资金约束，会计核心沉淀不可篡改的会计事实。

### 2.2 本期范围

| 模块 | 本期包含 | 本期不包含 |
| --- | --- | --- |
| 账户主体 | 用户、商户、平台、渠道、内部过渡户 | 复杂集团多层级资金池 |
| 账户类型 | 可用户、冻结户、待清算户、收入户、成本户、应收/应付户 | 资产证券化、复杂授信账户 |
| 交易能力 | 开户、充值入账、支付扣款、退款、冻结/解冻、商户结算、手续费入账 | 跨境清算、多币种汇兑损益 |
| 账务前置 | 入账规则配置、业务事件订阅、规则匹配、入账指令流水、指令执行流水 | 复杂规则引擎可视化编排 |
| 会计核心 | 会计科目、分录模板、复式记账、试算平衡、日终批次、对账 | 总账系统替代、税务申报 |
| 后台 | 账户查询、流水查询、冻结处理、会计凭证查询、对账差异处理 | 复杂 BI 分析平台 |

## 3. 设计原则

1. **业务与会计分离**：业务账户记录用户视角余额，会计核心记录财务视角借贷事实。
2. **余额由流水推导并可快照**：余额更新必须绑定流水，禁止无流水改余额。
3. **复式记账必平**：每张会计凭证借方金额合计必须等于贷方金额合计。
4. **幂等优先**：所有资金类指令必须以业务请求号保证幂等。
5. **先冻结后扣减**：存在履约风险或异步确认的交易优先走冻结/解冻/确认链路。
6. **可追溯不可物理删除**：账户、流水、凭证只允许状态变更或冲正，不允许物理删除。

## 5. 账务前置设计

### 5.1 定位与职责

账务前置位于业务账户和会计核心之间，负责把业务系统产生的事件转换为可执行、可追踪、可重试的入账指令。它不直接承担复式记账规则，而是将“什么业务事件需要入账、应该走哪类入账动作、需要生成几条账户/会计处理指令”配置化。

核心职责：

1. 接收订单、支付、结算、运营后台等系统发布的业务事件。
2. 根据事件类型、业务场景、主体类型、金额字段、状态条件匹配入账规则。
3. 生成入账指令流水，作为业务事件到后续账务处理的桥梁。
4. 调用账户服务和记账网关执行指令，沉淀指令执行流水。
5. 支持失败重试、人工补偿、规则版本追踪和审计。

### 5.2 入账规则配置

| 配置项 | 说明 | 示例 |
| --- | --- | --- |
| rule_id | 规则 ID | AR_PAY_SUCCESS_001 |
| rule_name | 规则名称 | 支付成功入账规则 |
| event_type | 触发事件类型 | PAYMENT_SUCCESS |
| biz_scene | 业务场景 | WALLET_PAY、CARD_PAY、REFUND |
| match_condition | 匹配条件 | order_status = SUCCESS 且 amount > 0 |
| priority | 匹配优先级 | 100 |
| effective_time | 生效时间 | 2026-04-25 00:00:00 |
| expire_time | 失效时间 | 可为空 |
| rule_version | 规则版本 | v3 |
| status | 规则状态 | 草稿、待审批、生效、停用 |
| instruction_template | 入账指令模板 | 冻结扣减、商户待结算入账、手续费入账 |

规则配置原则：

- 同一事件在同一场景下只能命中一条主规则，避免重复入账。
- 规则变更必须生成新版本，历史指令保留命中的规则版本。
- 生效规则必须经过审批，停用规则不得影响已生成的入账指令。
- 金额字段、主体字段和账户字段必须来自事件白名单，避免任意表达式访问敏感数据。
- 规则只能生成标准入账指令，不能绕过账户服务直接改余额。

指令模板字段：

| 字段 | 说明 | 示例 |
| --- | --- | --- |
| instruction_type | 入账指令类型 | BALANCE_DEDUCT |
| account_action_type | 账户动作类型 | FREEZE_TO_DEDUCT、INCREASE_AVAILABLE |
| source_account_selector | 来源账户选择器 | participants.user.account_no |
| target_account_selector | 目标账户选择器 | participants.merchant.settle_account_no |
| amount_expression | 金额表达式 | amount - fee_amount |
| accounting_trade_type | 会计交易类型 | USER_PAY_SUCCESS |
| execute_order | 执行顺序 | 1 |
| compensation_policy | 补偿策略 | RETRY、MANUAL_REVIEW |

### 5.3 事件触发与规则匹配

```text
业务系统发布事件
  -> 账务前置接收事件
  -> 校验事件幂等号和事件签名
  -> 按 event_type + biz_scene 筛选候选规则
  -> 执行匹配条件
  -> 锁定规则版本
  -> 生成入账指令流水
  -> 推送账务处理执行
```

事件标准字段：

| 字段 | 说明 | 是否必填 |
| --- | --- | --- |
| event_id | 事件唯一 ID，用于事件幂等 | 是 |
| event_type | 事件类型 | 是 |
| biz_scene | 业务场景 | 是 |
| biz_order_no | 业务单号 | 是 |
| occurred_at | 事件发生时间 | 是 |
| amount | 主金额，单位分 | 视场景 |
| currency | 币种 | 是 |
| participants | 参与方信息，如用户、商户、渠道 | 是 |
| payload | 业务扩展字段 | 否 |

匹配失败处理：

- 未找到规则：事件进入“待配置”状态，告警给产品/财务配置人员。
- 命中多条规则：事件进入“规则冲突”状态，不生成入账指令。
- 规则字段缺失：事件进入“数据异常”状态，支持业务方补发修正事件。

### 5.4 入账指令流水

入账指令流水记录“根据某个业务事件准备做什么账务处理”，是账务前置的核心产物。

| 字段 | 说明 |
| --- | --- |
| instruction_no | 入账指令号 |
| event_id | 来源事件 ID |
| request_id | 账务幂等请求号 |
| rule_id | 命中的入账规则 ID |
| rule_version | 命中的规则版本 |
| biz_order_no | 业务单号 |
| instruction_type | 指令类型，如 BALANCE_FREEZE、BALANCE_DEDUCT、MERCHANT_SETTLE_IN、ACCOUNTING_ONLY |
| account_actions | 账户动作集合 |
| accounting_trade_type | 会计交易类型 |
| amount | 指令金额，单位分 |
| status | 待执行、执行中、执行成功、执行失败、已取消、待人工处理 |
| retry_count | 重试次数 |
| created_at | 创建时间 |

指令状态流转：

```text
待执行 -> 执行中 -> 执行成功
   |         |
   v         v
已取消    执行失败 -> 待人工处理 -> 执行成功
```

### 5.5 指令执行流水

账务处理执行入账指令后，必须产生指令执行流水，记录每一次执行尝试、账户处理结果和会计处理结果。

| 字段 | 说明 |
| --- | --- |
| execution_no | 执行流水号 |
| instruction_no | 入账指令号 |
| execution_seq | 第几次执行 |
| executor | 执行器，如 ACCOUNT_SERVICE、ACCOUNTING_GATEWAY |
| execute_status | 成功、失败、处理中、已回滚 |
| account_journal_no | 关联业务账户流水 |
| voucher_no | 关联会计凭证号 |
| error_code | 失败编码 |
| error_message | 失败说明 |
| started_at | 开始时间 |
| finished_at | 结束时间 |

执行规则：

1. 一条入账指令可以有多条执行流水，但只能有一条最终成功流水。
2. 账户处理成功、会计处理失败时，指令标记为“待补记”，执行流水保留账户流水号。
3. 会计处理成功、账户处理失败的场景原则上不允许发生；若发生，进入差错过渡户并告警。
4. 重试必须沿用原 instruction_no 和 request_id，避免重复入账。
5. 人工补偿必须生成新的执行流水，并记录操作者和审批单号。

一致性规则：

- 账户执行成功后才允许发起会计核心记账；需要会计先行校验的场景只做模板预校验，不落正式凭证。
- 同一 instruction_no 下的执行流水必须按 execution_seq 递增，后一次执行必须能引用上一次失败原因。
- 指令最终成功后，账户流水号和会计凭证号必须回写入账指令流水，方便从事件、指令、执行、账户流水、会计凭证双向追踪。
- 执行失败且达到最大重试次数后，指令进入待人工处理，不再自动重试。

## 6. 业务账户设计

### 6.1 核心概念

| 概念 | 说明 | 示例 |
| --- | --- | --- |
| 账户主体 | 持有账户的业务对象 | 用户、商户、平台、支付渠道 |
| 账户 | 主体名下承载某类资金的容器 | 用户余额账户、商户待结算账户 |
| 账户子类型 | 按资金状态或业务用途拆分 | 可用、冻结、待清算、手续费 |
| 业务流水 | 对账户余额产生影响的业务记录 | 支付扣款流水、退款入账流水 |
| 余额快照 | 某一时点账户余额汇总 | 日终余额、实时余额 |

### 6.2 账户主体

| 字段 | 说明 | 规则 |
| --- | --- | --- |
| subject_id | 主体 ID | 全局唯一 |
| subject_type | 主体类型 | USER、MERCHANT、PLATFORM、CHANNEL、INTERNAL |
| subject_name | 主体名称 | 展示与检索使用 |
| cert_status | 实名/资质状态 | 未认证、已认证、冻结 |
| status | 主体状态 | 正常、限制交易、注销 |
| created_at | 创建时间 | 系统生成 |

### 6.3 账户类型

| 账户类型 | 所属主体 | 资金含义 | 是否可交易 |
| --- | --- | --- | --- |
| USER_AVAILABLE | 用户 | 用户可直接消费或提现的余额 | 是 |
| USER_FROZEN | 用户 | 用户因支付、风控、争议被冻结的余额 | 否 |
| MERCHANT_SETTLE_PENDING | 商户 | 已交易成功但未到结算周期的资金 | 否 |
| MERCHANT_AVAILABLE | 商户 | 商户可提现或可抵扣的余额 | 是 |
| PLATFORM_FEE_INCOME | 平台 | 平台手续费收入 | 否，财务处理 |
| CHANNEL_CLEARING | 渠道 | 渠道侧在途或待清算资金 | 否 |
| INTERNAL_SUSPENSE | 内部 | 异常、待确认或差错过渡资金 | 否 |

### 6.4 账户状态

```text
待激活 -> 正常 -> 冻结 -> 正常
             |       |
             v       v
           注销 <- 限制出金
```

| 状态 | 可入金 | 可出金 | 可冻结 | 说明 |
| --- | --- | --- | --- | --- |
| 待激活 | 否 | 否 | 否 | 开户成功但认证或审核未完成 |
| 正常 | 是 | 是 | 是 | 默认可交易状态 |
| 限制出金 | 是 | 否 | 是 | 风控或合规限制 |
| 冻结 | 否 | 否 | 否 | 整体账户冻结 |
| 注销 | 否 | 否 | 否 | 余额清零后关闭 |

### 6.5 账户余额模型

| 字段 | 说明 |
| --- | --- |
| account_id | 账户 ID |
| currency | 币种，默认 CNY |
| available_amount | 可用余额 |
| frozen_amount | 冻结余额 |
| pending_amount | 在途余额 |
| total_amount | 总余额，通常为 available + frozen + pending |
| version | 乐观锁版本 |
| updated_at | 最近更新时间 |

余额更新规则：

1. 金额精度以分为最小单位存储，展示层转换为元。
2. 余额更新必须校验账户状态、交易方向、余额是否足额。
3. 每次余额变更生成业务流水，并关联会计凭证号。
4. 并发更新采用账户维度乐观锁或账户分片锁。
5. 冲正交易不能直接删除原流水，应生成反向流水。

#### 6.6.1 账户列表页

```text

+---------------------------------------------------------------+
```

#### 6.6.3 冻结/解冻弹窗

```text
+------------------------------------------+
| 冻结资金                                  |
+------------------------------------------+
| 账户ID：A001                              |
| 可用余额：100.00 CNY                      |
| 冻结金额：[________]                      |
| 冻结原因：[风控/争议/司法/运营调整 v]      |
| 备注：[______________________________]    |
| 附件：[上传]                              |
+------------------------------------------+
| [取消]                           [提交]   |
+------------------------------------------+
```

校验：

- 冻结金额必须大于 0 且小于等于可用余额。

- 解冻必须选择原冻结流水，避免无来源解冻。

## 7. 会计核心设计

### 7.1 核心概念

| 概念 | 说明 |
| --- | --- |
| 会计科目 | 财务记账的分类载体，如银行存款、用户负债、手续费收入 |

## 8. 核心业务流程

### 8.1 事件驱动入账主链路

所有会影响账户余额或会计凭证的业务动作，统一先沉淀为业务事件，再由账务前置匹配入账规则并生成入账指令流水。账务处理组件执行指令时，分别调用账户服务和记账网关，并为每次执行尝试生成指令执行流水。

```text
业务动作完成
  -> 发布标准业务事件
  -> 账务前置校验事件幂等与签名
  -> 匹配生效入账规则并锁定规则版本
  -> 生成入账指令流水
  -> 账务处理执行指令
  -> 产生指令执行流水
  -> 账户服务生成业务账户流水
  -> 记账网关/会计核心生成会计凭证
```

链路约束：

- 业务事件是入账触发源，不能由运营直接跳过事件创建成功入账结果。
- 入账规则决定是否入账、入账类型、账户动作和会计交易类型。
- 入账指令流水记录“要执行什么”，指令执行流水记录“实际执行了什么结果”。
- 账户流水、会计凭证必须能反查到 instruction_no、event_id 和规则版本。

### 8.2 开户流程

```text
业务方提交开户申请
  -> 校验主体资质
  -> 创建账户主体
  -> 按账户模板创建账户
  -> 初始化余额为 0
  -> 返回账户 ID
```

异常处理：

- 主体已存在：返回既有主体信息，不重复创建。
- 账户模板缺失：开户失败并提示配置缺失。
- 部分账户创建失败：整体回滚，避免主体下账户不完整。

### 8.3 用户充值流程

```text
用户发起充值
  -> 支付渠道收款
  -> 渠道回调成功
  -> 支付系统发布 RECHARGE_SUCCESS 事件
  -> 账务前置匹配“用户充值成功”入账规则
  -> 生成入账指令流水：USER_AVAILABLE_IN + ACCOUNTING_RECHARGE
  -> 账务处理执行指令并生成指令执行流水
  -> 账户服务增加用户可用余额并生成业务流水
  -> 会计核心生成充值凭证
  -> 返回充值成功
```

关键校验：

- 渠道回调必须校验签名。
- 同一渠道订单号只能成功入账一次。
- 事件重复投递时，按 event_id 返回既有入账指令流水。
- 账户入账成功但凭证失败时，指令执行流水标记会计处理失败，并进入待补记队列。

### 8.4 用户支付流程

```text
提交订单
  -> 校验用户可用余额
  -> 发布 PAYMENT_APPLY 事件
  -> 账务前置匹配“支付申请冻结”规则
  -> 生成并执行冻结入账指令
  -> 商户履约或支付确认
  -> 发布 PAYMENT_SUCCESS 事件
  -> 账务前置匹配“支付成功入账”规则
  -> 生成入账指令流水：冻结扣减、商户待结算入账、手续费入账
  -> 账务处理产生指令执行流水
  -> 账户服务扣减用户冻结余额、增加商户待结算余额
  -> 会计核心计提平台手续费
  -> 生成会计凭证
```

失败处理：

- 冻结后订单取消：解冻原冻结流水。
- 扣款成功但商户入账失败：进入差错过渡户并告警。
- 手续费入账规则或分录模板缺失：入账指令进入待人工处理，不生成成功账户流水。

### 8.5 退款流程

```text
业务方发起退款
  -> 校验原支付单和可退金额
  -> 锁定原交易
  -> 发布 REFUND_SUCCESS 事件
  -> 账务前置匹配退款入账规则
  -> 生成入账指令流水：商户/平台退款扣减、用户余额入账、手续费退还
  -> 账务处理执行指令并记录执行流水
  -> 账户服务扣减商户待结算或平台垫付账户、增加用户可用余额
  -> 会计核心按规则退还手续费
  -> 生成退款凭证
```

关键规则：

- 支持部分退款，多次退款累计金额不能超过原支付金额。
- 已结算交易退款需要走商户可用余额或应收款链路。
- 跨会计期间退款不能修改原凭证，只能生成新退款凭证。

### 8.6 商户结算流程

```text
结算周期到达
  -> 计算可结算订单
  -> 生成结算单
  -> 发布 SETTLEMENT_READY 事件
  -> 账务前置匹配“商户待结算转可提现”规则
  -> 生成并执行待结算转可提现入账指令
  -> 发起银行出款
  -> 出款成功后发布 SETTLEMENT_PAYOUT_SUCCESS 事件
  -> 账务前置生成出款扣减入账指令
  -> 账务处理记录指令执行流水并扣减商户可提现
  -> 生成结算凭证
```

异常处理：

- 银行出款失败：商户可提现余额保持不变，结算单标记失败。
- 银行处理中：金额进入在途状态，成功或失败后关闭在途。
- 对账不平：停止自动结算，进入差异处理。

## 11. 对账与监控

### 11.1 对账维度

| 对账项 | 对账口径 | 差异处理 |
| --- | --- | --- |
| 业务订单 vs 账户流水 | 成功订单金额等于账户流水金额 | 补流水或冲正订单 |
| 业务事件 vs 入账指令 | 需入账事件必须生成唯一入账指令 | 补发事件或补生成指令 |
| 入账指令 vs 指令执行流水 | 每条执行中或终态指令必须有执行流水 | 重试执行或转人工处理 |
| 账户流水 vs 会计凭证 | 每条资金流水有对应凭证 | 补记凭证 |
| 会计凭证借贷 | 借方合计等于贷方合计 | 阻断过账 |
| 渠道账单 vs 平台账户 | 渠道成功金额等于平台入账金额 | 渠道差错处理 |
| 日终余额 vs 流水汇总 | 期初 + 本期发生 = 期末 | 重算快照并定位异常流水 |

### 11.2 监控指标

- 记账成功率、记账失败率。
- 凭证借贷不平数量。
- 账户余额为负数量。
- 入账规则匹配失败数量、规则冲突数量。
- 入账指令执行失败数量、待人工处理数量。
- 待补记凭证数量和最长等待时间。
- 对账差异金额和笔数。
- 手工资金操作次数和审批超时数量。

## 12. 验收标准

1. 支持用户、商户、平台、渠道、内部户的开户和账户查询。
2. 支持配置入账规则，并按事件类型、业务场景、匹配条件和规则版本命中规则。
3. 需入账业务事件能生成唯一入账指令流水，重复事件不会重复生成成功指令。
4. 账务处理执行入账指令时必须生成指令执行流水，记录账户流水号、会计凭证号或失败原因。
5. 所有余额变化必须生成业务流水，流水可追溯到业务单号、事件 ID 和入账指令号。
6. 充值、支付、退款、结算至少四类交易能生成借贷平衡的会计凭证。
7. 同一 request_id 重复请求时返回同一处理结果，不重复入账。
8. 账户余额不足时支付、冻结、出款必须失败且不产生成功流水。
9. 凭证借贷不平时禁止过账，并可在后台查询失败原因。
10. 日终试算平衡页面可以展示借方合计、贷方合计、差额和明细。
11. 手工冻结、解冻、冲正和人工补偿均记录审批和操作日志。
